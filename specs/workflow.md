# 작업 분담 규칙 — Fable / Opus

Claude 요금제의 주간 한도가 "모든 모델"과 "Fable 전용"으로 나뉘어 있다. Fable 한도가 먼저 바닥나지 않도록 **일감을 Opus에게도 나눈다.** 개발 세션은 시작할 때 이 파일을 HANDOFF.md 다음으로 읽는다.

## 1. 기본 분담 (한도에 여유가 있을 때)

| 일 | 담당 |
| --- | --- |
| 기획·지시서(`specs/`)·검토 문구 | Opus (기획 채팅) |
| `core/`를 새로 설계하거나 크게 바꾸는 일 (새 러너, 새 시각화 엔진, 새 문제 type, 저장 스키마) | Fable |
| 콘텐츠: `courses/*/content.js`의 레슨·문제·힌트·코치, `shared/`의 용어·에러·뱃지 문구, `IMAGES.md` 요청서 | Opus |
| 지시서에 단계와 파일이 구체적으로 적힌 `core/` 수정 (예: NEXT.md WP-B 4·5단계, EXPANSION 14-8 표) | Opus 가능 — 3절 규칙 |
| 실사용 피드백 패치 (스크린샷) | 둘 다. 작은 것은 Opus |
| `[core]` 커밋 검토 | Fable (4절 체크리스트) |

## 2. 모드는 세션마다 사용자가 정한다

Claude는 사용량 화면을 볼 수 없으므로 모드를 문서에 고정하지 않는다. 사용자가 개발 채팅 첫 메시지에 둘 중 하나를 적는다.

| 모드 | 언제 (사용자 판단 기준 예시) | 동작 |
| --- | --- | --- |
| **기본** | Fable 전용 한도에 여유가 있을 때 | 1절 분담대로 |
| **Fable 절약** | Fable 전용 한도가 모든 모델 한도보다 많이 앞서 있을 때 | Opus가 전부 만든다(`core/` 수정도 지시서가 있으면). Fable은 `[core]` 커밋 검토만 하고 새 기능을 시작하지 않는다 |

- 첫 메시지에 모드가 없으면 **한 번만 묻는다**("기본 / Fable 절약 중 어느 모드로 할까요?"). 답이 없으면 기본.
- 모드는 그 채팅 안에서만 유효하다. 문서·상태판에 "지금 모드"를 적지 않는다.

## 3. Opus 개발 세션 규칙

1. 시작: 저장소를 최신으로 당기고(`git fetch` + `reset --hard origin/main`), HANDOFF.md → 이 파일 → 맡은 지시서 순서로 읽는다. 다른 채팅이 그 사이 푸시했을 수 있으니 **푸시 직전에도 다시 당긴다.**
2. 범위: 지시서에 적힌 파일만 고친다. 지시서에 없는 `core/` 파일을 고쳐야 하면 멈추고 사용자에게 "이 파일도 고쳐야 한다, Fable 검토 대상"이라고 알린다.
3. 검증(푸시 전 필수): `node tools/validate_content.mjs && node tools/extract.mjs tools/.out && python3 tools/run_solutions.py`, 셸 관련이면 `node tools/test_shell.mjs`, 가능하면 `python3 tools/regress.py`.
4. 커밋 메시지: `core/`를 한 줄이라도 바꿨으면 맨 앞에 **`[core]`**. 예: `[core] v2.3.0: 터미널 러너 디스패치`. 콘텐츠만이면 표시 없음.
5. HANDOFF 상태판·CHANGELOG는 기존 규칙대로 같은 커밋에. 상태판 "마지막 작업"에 **작업한 모델(Opus/Fable)**을 괄호로 적는다.
6. 사용자에게 보고할 때: 버전, 바뀐 것 한 줄, 브라우저에서 확인할 곳(어느 화면 → 어느 문제), `[core]`였는지 여부.

## 4. Fable 검토 체크리스트 (`[core]` 커밋만)

`git log --oneline --grep "\[core\]"`로 목록을 뽑고 커밋마다:

- [ ] 다른 코스(파이썬·알고리즘)의 동작을 바꿨나 — 바뀐 함수의 호출처를 `grep`
- [ ] 저장 데이터 모양을 바꿨나 — 바꿨다면 예전 데이터가 그대로 읽히나
- [ ] 전역 이름·스크립트 로드 순서·`?v=` 규칙을 지켰나
- [ ] 모바일 390px, 다크/라이트, 접근성 설정(고대비·아주 크게)에서 깨지지 않나 (`regress.py`)
- [ ] 지시서와 다르게 만든 부분이 DESIGN.md에 이유와 함께 적혀 있나
- 문제가 있으면 패치 커밋, 없으면 HANDOFF 상태판에 "Fable 검토 통과: 커밋 해시들" 한 줄.

## 5. 작업 순서는 HANDOFF 상태판이 기준

무엇을 먼저 할지는 HANDOFF.md 0절 "다음 후보"가 정한다(이 파일에 적지 않는다). 다만 순서를 정할 때 지킬 것:

- `core/engine.js`·`core/ui-views-main.js`처럼 **같은 `core` 파일을 건드리는 작업 두 개를 동시에 두 채팅으로 돌리지 않는다.** 하나를 배포한 뒤 다음을 시작한다.
- 콘텐츠만 건드리는 작업(서로 다른 `courses/<id>/content.js`)은 동시에 돌려도 된다. 푸시 직전에 다시 당긴다.

## 6. 버전 번호

문서들에 적힌 마이너 번호(NEXT.md "WP-B = 2.3.0", EXPANSION 14절 "M1 = 2.3.0", "SQL 2.4.0" 등)는 **순서 표시일 뿐**이다. 실제 번호는 **먼저 배포되는 쪽이 다음 마이너를 가져간다.** 배포할 때 NEXT.md 표와 EXPANSION.md의 해당 줄을 실제 번호로 고친다. 예: 터미널·Git이 먼저 배포되면 v2.3.0, 그다음 수학 M1은 v2.4.0.
